# Capturing a specific window by handle on Windows 11

**Research date:** 2026-08-04
**Scope:** Windows desktop app that screenshots a user-selected Chrome/Edge window on a timed interval and sends the image to a vision LLM. Full-screen capture is rejected on privacy grounds. Target machine has Node 24/npm; no Python, .NET, or Rust toolchain installed.

## Bottom line up front

**Target the Windows Graphics Capture (WGC) API** (`Windows.Graphics.Capture`, reached via `IGraphicsCaptureItemInterop::CreateForWindow`), not `PrintWindow`. WGC is the only one of the candidate APIs that (a) reliably captures GPU-composited Chrome/Edge content, (b) captures occluded/background windows, and (c) is actually reachable from this machine's toolchain (Node 24, no Python/.NET/Rust) via a prebuilt npm package. Its one real cost is a system-drawn yellow border on the local display while capturing — see §7 for the (packaging-gated) way to suppress it.

The pragmatic implementation path for this stack is **Electron's `desktopCapturer`**, which on Windows is backed by Chromium's `WgcCapturerWin` (i.e., WGC under the hood) — see §6. If Electron is not the chosen shell, the fallback is a small native Node addon or an out-of-process helper calling the WGC interop APIs directly.

## 1. Candidate APIs

### PrintWindow (GDI)
- Win32, `user32.dll`, signature `BOOL PrintWindow(HWND hwnd, HDC hdcBlt, UINT nFlags)`. Minimum supported client: Windows XP. [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow)
- Sends the target window a `WM_PRINT`/`WM_PRINTCLIENT` message and expects the window to paint itself into the supplied DC. It is a **synchronous, blocking** call — the docs explicitly warn it "might not return immediately" and can make a UI thread appear unresponsive.
- `nFlags` officially only documents `PW_CLIENTONLY` (client area only vs. whole window). The commonly-used `PW_RENDERFULLCONTENT` (value `2`) is **not present in the official parameter table** — it is only known from the Rust `windows` crate constant definitions and community reverse-engineering, and is described everywhere as an **undocumented** flag that happens to work since Windows 8.1. [Rust windows-rs constant](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/UI/WindowsAndMessaging/constant.PW_RENDERFULLCONTENT.html)
- Without `PW_RENDERFULLCONTENT`, GPU-composited windows (Chrome, Edge, most modern Electron/Chromium apps) render as a **black rectangle**, because the content lives in the GPU/DirectComposition swap chain rather than in anything GDI can see. With `PW_RENDERFULLCONTENT`, Chromium can usually be coerced into producing real pixels because the flag forces the app to render its full DirectComposition-backed content into the DC — but because it is undocumented, Microsoft gives no compatibility guarantee, and several reports (Chromium's own graphics-dev group, AutoHotkey forums, Stack Overflow-adjacent threads) describe it as **unreliable across Chromium versions/GPU configurations** rather than a guaranteed fix. [Chromium graphics-dev thread](https://groups.google.com/a/chromium.org/g/graphics-dev/c/LrpgdDg7p_8)

### Windows.Graphics.Capture (WinRT, Win10 1803+)
- Namespace `Windows.Graphics.Capture`, introduced Windows 10 April 2018 Update (1803). Win32 interop (`CreateForWindow(HWND)`, `CreateForMonitor(HMONITOR)`) shipped in the May 2019 Update (1903), via `windows.graphics.capture.interop.h` / `IGraphicsCaptureItemInterop`. [Microsoft Learn — CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), [Windows Developer Blog, 2019-09-16](https://blogs.windows.com/windowsdeveloper/2019/09/16/new-ways-to-do-screen-capture/)
- Model: create a `GraphicsCaptureItem` for the HWND → create a `Direct3D11CaptureFramePool` sized to `item.Size` → create a `GraphicsCaptureSession` from the pool → `StartCapture()` → pull frames via `FrameArrived` or `TryGetNextFrame`. Frames arrive as GPU surfaces (`Direct3D11CaptureFrame.Surface`, DXGI format `B8G8R8A8_UNORM`, or `R16G16B16A16_FLOAT` for HDR content) that must be copied out (e.g., to a `CanvasBitmap` or staged to a CPU-readable texture) before saving as PNG/JPEG. [Microsoft Learn — Screen capture how-to, updated 2026-05-13](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)
- Because it operates on the DWM's actual composited surface (the same pixels the user sees), it is **compositor-native**: it does not care whether the target uses GPU acceleration, DirectComposition, or any particular rendering pipeline. This is the fundamental reason it sidesteps the PrintWindow black-frame problem.
- Availability should be checked at runtime with `GraphicsCaptureSession.IsSupported()` — not all devices/drivers support it.
- Resizing/moving the target window does not require re-picking it: the frame pool delivers new frame sizes and the app calls `Direct3D11CaptureFramePool.Recreate` to resize its buffers; `GraphicsCaptureItem` also exposes a `Closed` event for when the target window is destroyed. [Microsoft Learn — Screen capture how-to](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)

### Desktop Duplication API + crop
- `IDXGIOutputDuplication` captures an entire output (monitor), not a window. To get "just the window" you must crop the monitor-sized frame to the window's screen rectangle. This means:
  - You always decode/transfer full-monitor pixel data even though you only want a sub-region — worse for privacy (a bug or memory dump exposes the whole screen, not just the target window) and worse for bandwidth/perf on high-res monitors.
  - Any window on top of yours (another app's floating window, a tooltip, a notification toast) bleeds into the crop, since you're literally capturing what's on screen at that pixel location — this is a **correctness** problem for occlusion, not just a privacy one.
  - It cannot capture a window that's fully covered or off the visible monitor region (e.g., minimized, or on a monitor a user just unplugged) at all, since there's no monitor surface to sample from.
  - Given the app's explicit privacy requirement to avoid full-screen capture, desktop-duplication-plus-crop is a poor fit even though it is technically reachable and avoids the GPU black-frame problem (it, like WGC, samples the compositor's output).

## 2. The GPU-accelerated Chrome problem

This is real, well documented, and current behavior, not a legacy issue:

- Chromium's own graphics-dev mailing list confirms: **"`PrintWindow()` does not work with Chrome — it prints a black rectangle only"** when GPU compositing is enabled, and that `PW_RENDERFULLCONTENT` (undocumented, Windows 8.1+) is the community workaround. [Chromium graphics-dev group](https://groups.google.com/a/chromium.org/g/graphics-dev/c/LrpgdDg7p_8)
- The root cause: with hardware acceleration on, the browser's rendered pixels live in a GPU/DirectComposition swap chain that the classic GDI `BitBlt`/`PrintWindow` path never sees — the CPU-side DC for that window is left black because compositing happens entirely on the GPU side, and GDI capture predates that pipeline.
- Practical mitigations reported in the wild (forums, not Microsoft-sanctioned): disabling Chrome's hardware acceleration (defeats the purpose — you don't control the user's browser config), or passing `--disable-gpu-compositing` (a restart-requiring Chrome flag you cannot force on a user's normal browser).
- **Which API avoids it:** Windows.Graphics.Capture, because (per §1) it captures the DWM-composited surface directly rather than asking the target app to redraw into a GDI DC. Chromium's own WebRTC `desktop_capture` module — which backs `getDisplayMedia()`, Chrome's screen-sharing, and (transitively) Electron's `desktopCapturer` — ships a dedicated `WgcCapturerWin` implementation specifically to solve this class of problem for window sources on Windows, alongside a legacy `WindowCapturerWinGdi` used as a fallback path. [`wgc_capturer_win.cc`, Chromium/WebRTC](https://webrtc.googlesource.com/src/+/lkgr/modules/desktop_capture/win/wgc_capturer_win.cc)

**Conclusion:** for reliably screenshotting a live Chrome/Edge window, PrintWindow (even with `PW_RENDERFULLCONTENT`) is a best-effort, undocumented hack; WGC is the supported, compositor-native solution.

## 3. Occlusion and background windows

- **WGC:** Because it captures the DWM's composited output for that specific window, it can capture the window while it is **partially covered by other windows and while it is not focused/not the foreground window**. This is the entire point of the API relative to GDI methods — no window-must-be-visible-and-on-top requirement exists in the documented model (contrast with the old `BitBlt`-from-screen-DC approach, which is destroyed by occlusion). No official doc explicitly enumerates "capture while occluded" as a bullet point, but it follows directly from operating on the composited swap chain rather than screen pixels, and is consistent with why WGC/Windows' own screen/window-sharing features (Teams, Discord, OBS's Windows 10+ "Windows Graphics Capture" source) work when the shared window is behind other windows.
- **PrintWindow:** Also does not strictly require the window to be on top on screen (it asks the app to paint into an off-screen DC), but this is precisely the code path that fails to produce real content for GPU-composited apps (§2) — so in practice, for Chrome/Edge, occlusion tolerance is moot because the base capture is already broken.
- **Desktop Duplication + crop:** Explicitly **cannot** handle occlusion correctly — anything on top of the target window at that screen location is what gets captured, since you're sampling monitor pixels, not the specific window's composited surface (§1).

## 4. Minimized windows and virtual desktops

- **The OS itself stops rendering/composing a window once it's minimized.** This is the root constraint every capture API inherits — there is no live composited surface to sample. [Microsoft Q&A discussion](https://learn.microsoft.com/en-us/answers/questions/5516715/winrt-windows-graphics-capture-leads-to-applicatio), [OBS forum discussion of the same limitation](https://obsproject.com/forum/threads/how-to-capture-minimized-window.167081/)
- For **WGC**, the commonly reported behavior (community sources, not an explicit Microsoft doc statement) is that the frame pool simply **stops delivering new frames** while the window is minimized — the last successfully captured frame is what you're left holding, i.e. **stale content**, not a fresh black frame. Treat this as reasonably well-corroborated but not formally documented; do not rely on it as a guarantee.
- For **PrintWindow**, a minimized window typically yields a **black or garbage frame** since there's no live GDI-renderable surface either.
- **Virtual desktops:** a window that's minimized or on another virtual desktop is functionally in the same "not currently composed" state. There is no Microsoft-documented distinction between "minimized" and "on another virtual desktop" for capture purposes — both remove the window from active composition.
- **Practical implication for this app:** since the app polls on a timer and sends frames to a vision LLM, it must detect the "not currently capturable" state (e.g., via `IsIconic(hwnd)` for minimized, or by checking whether `GraphicsCaptureItem`/frame delivery has gone stale) and either skip that capture cycle or surface a "window is minimized, capture paused" state to the user rather than silently sending stale/black frames to the LLM.

## 5. Per-monitor DPI

- Windows exposes DPI in two now-relevant flavors: system DPI (global) and **per-monitor DPI** (Windows 8.1+ `PROCESS_PER_MONITOR_DPI_AWARE`, refined further in Windows 10 with per-monitor-v2 and thread-level DPI contexts declared via the app manifest `<dpiAwareness>`). [Microsoft Learn — High DPI desktop app development](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)
- **GDI-based capture (PrintWindow/BitBlt) is DPI-awareness-sensitive on the *capturing* process's side.** A documented failure mode (raised in an OBS Studio issue): if the capturing process and the target window are system-DPI-aware under *different* effective DPI settings, `GetClientRect()`/`GetWindowRect()` resolve coordinates using the capturing thread's current DPI awareness context, producing an **incorrect capture rectangle size** relative to what the target window actually occupies. [OBS Studio issue #8706](https://github.com/obsproject/obs-studio/issues/8706) Concretely: your process must declare itself Per-Monitor-V2 DPI aware (via manifest or `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`) and use `GetDpiForWindow`/`GetDpiForMonitor` to convert logical window rects into physical pixel rects correctly, otherwise the bitmap you get from GDI capture will be wrong-sized or offset when the browser window is on a monitor with a scale factor different from the primary monitor or from what your process assumed at startup.
- **WGC largely sidesteps this**: `GraphicsCaptureItem.Size` and the resulting `Direct3D11CaptureFrame` surfaces are dimensioned in the window's actual **physical/composited pixel size** — you size your `Direct3D11CaptureFramePool` directly from `item.Size` with no separate DPI conversion step in the documented flow, because WGC hands you the same physical-pixel surface DWM already composited (which DWM itself already resolved for the monitor the window is on). [Microsoft Learn — Screen capture how-to](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) The official reference for `GraphicsCaptureItem.Size` doesn't spell out "physical vs logical" in prose, but the API's whole model (frame pool sized to `item.Size`, frames delivered as raw D3D surfaces) only makes sense if `Size` is the physical pixel size of the compositor's surface — logical/DPI-scaled units would produce a frame pool mismatched to the actual swap chain. Treat this as strongly implied by the API design and community consensus (robmikh's Win32CaptureSample and related blog posts), not an explicit documented guarantee.
- **What must be compensated for either way:** if the target window moves between monitors with different scale factors mid-session (e.g., 100% primary, 150% secondary), the pixel dimensions of the captured image will change between capture cycles even though the window's *logical* size didn't change. A downstream consumer (the vision LLM pipeline) that assumes a fixed image resolution needs to handle variable capture dimensions, or the app should normalize/resize before sending.

## 6. Runtime reach

### Electron — `desktopCapturer`
- Electron's `desktopCapturer.getSources({ types: ['window'] })` returns `DesktopCapturerSource` objects with an `id` you feed to `navigator.mediaDevices.getUserMedia` with `chromeMediaSourceId`. The **official Electron docs do not state which underlying Windows API it wraps** — that has to be sourced from Chromium/WebRTC itself. [Electron docs](https://www.electronjs.org/docs/latest/api/desktop-capturer)
- Tracing it to Chromium: `desktopCapturer` is Electron's wrapper around Chromium's `content::DesktopCaptureDevice`, which delegates to the WebRTC `desktop_capture` module. On Windows, that module ships two window capturers side by side: `WgcCapturerWin` (Windows.Graphics.Capture-based) and a legacy GDI-based capturer, with `WgcCapturerWin::CreateRawWindowCapturer` as the modern entry point. [`wgc_capturer_win.cc`](https://webrtc.googlesource.com/src/+/lkgr/modules/desktop_capture/win/wgc_capturer_win.cc) In other words: **using Electron's `desktopCapturer` for a window source is, in practice, going through WGC on modern Windows/Chromium**, giving you the GPU-composited-content benefit "for free" without hand-rolling WinRT interop — but this is an implementation detail of Chromium, not an Electron API contract, and could change between Chromium versions.
- **Reliability caveats specifically documented in Electron's own issue tracker** (not just general WGC caveats):
  - `getSources` on Windows has historically **excluded minimized windows and some standard windows** (e.g., Settings) from the returned list. [electron/electron#18417](https://github.com/electron/electron/issues/18417)
  - Electron's *own* windows were excluded from `getSources` results on Windows for several versions; a later patch (`add_current_process_windows`) fixed enumeration of the calling app's own windows, which doesn't affect capturing Chrome/Edge but shows the enumeration layer has had real bugs. [electron/electron#36037](https://github.com/electron/electron/issues/36037), [PR #45000](https://github.com/electron/electron/pull/45000)
  - Multi-monitor enumeration bugs have been reported (`getSources()` only detecting one screen in multi-screen setups). [electron/electron#22364](https://github.com/electron/electron/issues/22364)
  - Overall: `desktopCapturer` is usable but has a track record of edge-case enumeration bugs on Windows; test against the actual Electron version pinned in the project, not just against "Electron in general."
- **This is directly reachable from the stated toolchain** (Node 24/npm, Electron is an npm package) with no additional compiler needed — Electron ships prebuilt.

### Rust/Tauri crates
- **`windows-capture`** (`NiiightmareXD/windows-capture`, crates.io) — explicitly built on the WGC API ("Fastest Windows Screen Capture Library for Rust", wraps `Windows.Graphics.Capture`). Actively maintained: recent releases (v2.0.0 line) add DXGI Desktop Duplication support and hardware-accelerated encoding. [crates.io](https://crates.io/crates/windows-capture)
- **`xcap`** (`nashaofu/xcap`) — cross-platform (Windows/macOS/Linux X11+Wayland), the maintained **successor** to the now-deprecated `screenshots` and `screenshoter`/`screencapture` crates (those crates now point users to `xcap`). ~1,000+ GitHub stars, 140 forks, 44 open issues at time of research — moderately active, not a toy project. Windows screen and window capture are marked supported (✅) in its feature matrix; **window video recording is marked "to be developed"** (still WIP), and its own examples note **minimized windows cannot be screenshotted**. The exact underlying Win32/WinRT call `xcap` uses on Windows was not confirmed from the README (would require reading the Windows-specific source module directly); it should be verified in source before depending on it for the GPU-black-frame behavior specifically. [github.com/nashaofu/xcap](https://github.com/nashaofu/xcap)
- **`screenshots`** — deprecated, redirects users to `xcap`. Do not start new work on it.
- **Toolchain implication for this machine:** all three are Rust crates requiring a Rust toolchain to build from source. **This machine has no Rust toolchain installed.** However, `xcap` has a companion **prebuilt Node.js native addon, `node-screenshots`** (same author, nashaofu), which ships **prebuilt binaries** for Windows x64/x86/arm64 (and macOS/Linux) so it can be `npm install`ed on Node 16/18/20 **without compiling Rust locally** — the Rust toolchain is only needed by the maintainer to publish, not by consumers. [github.com/nashaofu/node-screenshots](https://github.com/nashaofu/node-screenshots) Its documented API (`Window.all()`, `captureImageSync()`/`captureImage()`) enumerates windows and captures them, but does not expose an obvious "track this HWND across moves/resizes as a persistent handle" primitive beyond re-querying `Window.all()` and capturing by id each cycle — workable for a timed-interval capture loop (re-resolve the window each tick), less elegant than a native "session" object.
- **`screenshots`** (unrelated node package for browser automation screenshotting, not the deprecated Rust crate) was not investigated — out of scope, this is about native window capture.

### Native C#/C++ path
- The documented, Microsoft-sanctioned way to reach WGC directly is C++/WinRT or C# with `Windows.Graphics.Capture.Interop.h` (`IGraphicsCaptureItemInterop::CreateForWindow`) — see robmikh's official-adjacent sample, `Win32CaptureSample`, and Microsoft's own `Windows.UI.Composition-Win32-Samples` repo (includes a WPF C# sample). This requires either the Windows SDK + Visual Studio (C++) or a .NET SDK (C#) — **both are explicitly unavailable on this machine** per the stated constraints. [robmikh/Win32CaptureSample](https://github.com/robmikh/Win32CaptureSample), [microsoft/Windows.UI.Composition-Win32-Samples](https://github.com/microsoft/Windows.UI.Composition-Win32-Samples/blob/master/dotnet/WPF/ScreenCapture/README.md)
- A theoretical Node-only path to raw WGC without Electron would be a **native N-API/node-gyp addon written in C++**, but that still requires a C++ compiler (MSVC via Build Tools) at minimum — also not currently installed. There's also a very old, essentially abandoned `@nodert-win10-20h1/windows.graphics.capture` npm package (NodeRT-generated WinRT projection), last published ~6 years ago at time of research — **not recommended**, effectively unmaintained. [npmjs.com](https://www.npmjs.com/package/@nodert-win10-20h1/windows.graphics.capture)

## 7. Capture indicator side effects

- **WGC draws a system-level yellow/orange border** around the captured window on the *local* display whenever a capture session is active, starting with Windows 11 22H2's "Screen Capture Indicator" privacy feature. This border is visible to the local user only — it is not baked into the captured frame content, so it won't appear in the image sent to the vision LLM, but it **will be visible on the user's own screen** the whole time the app is running, around whichever Chrome/Edge window is selected. This is confirmed to affect any app going through WGC — OBS Studio, Discord, Zoom, Teams are all cited as exhibiting it. [Windows Report](https://windowsreport.com/yellow-border-around-screen-windows-11/), [Microsoft Q&A — turning off the border via Settings > System > Display > Graphics](https://learn.microsoft.com/en-us/answers/questions/4172450/turn-off-the-yellow-screen-border-windows-11-uses)
- **It can be suppressed programmatically**, but with a real gate: `GraphicsCaptureSession.IsBorderRequired` (bool, settable) can turn the border off — but only after the app calls `GraphicsCaptureAccess.RequestAccessAsync(GraphicsCaptureAccessKind.Borderless)` and the **user explicitly consents** to a system prompt, **and** the app has declared the `graphicsCaptureWithoutBorder` **restricted capability in its package manifest**. [Microsoft Learn — `IsBorderRequired`](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired) This is a real complication for an unpackaged Win32/Electron app: restricted capabilities are normally an MSIX/Store-packaging concept, and it is not established from the docs gathered here that an unpackaged win32/Electron app can declare and be granted `graphicsCaptureWithoutBorder` at all — this needs to be spiked directly (e.g., try `RequestAccessAsync` from an unpackaged app and see whether the OS honors it, or whether packaging as MSIX becomes a hard requirement just to suppress the border). If the app cannot get this capability, **the yellow border is an unavoidable, permanent visual side effect** of using WGC on Windows 11 22H2+.
- The user-facing Settings toggle (System > Display > Graphics > "Screen capture border") is a **user preference**, not something the app can flip on the user's behalf without their action — relying on the user manually disabling it is not a viable product design.
- **PrintWindow** and **Desktop Duplication** do **not** draw this indicator (they predate/bypass the WGC-specific privacy feature) — this is the one respect in which they're less visually intrusive than WGC, at the cost of the GPU-compositing correctness problems documented in §2.

## Recommendation

1. **Target Windows.Graphics.Capture as the underlying capture mechanism.** It is the only candidate that reliably renders GPU-composited Chrome/Edge content (§2), tolerates occlusion and background windows (§3), and hands back physical-pixel-correct frames without the capturing process having to hand-roll DPI math (§5).
2. **Reach it via Electron's `desktopCapturer`.** On this machine's toolchain (Node 24/npm, no Python/.NET/Rust), Electron is the only path investigated that (a) transitively uses WGC through Chromium's `WgcCapturerWin`, (b) requires no local compiler, and (c) is a mature, actively maintained project with first-party docs. Budget time to work around its known Windows-side `getSources` enumeration quirks (minimized/standard windows sometimes missing, multi-monitor edge cases — §6) and to explicitly handle the minimized/virtual-desktop stale-frame case (§4) rather than forwarding stale or black frames to the vision LLM.
3. **Treat `node-screenshots`/`xcap` as a lighter-weight fallback worth a quick spike**, not a first choice sight-unseen — it avoids pulling in all of Electron, ships prebuilt for Node 16/18/20 with no Rust toolchain needed locally, but its exact Windows backend (WGC vs. GDI) was not confirmed from documentation alone in this research pass and should be verified empirically against a real Chrome/Edge window before relying on it.
4. **Plan for the yellow capture border as a permanent UX cost** unless a spike proves that an unpackaged Electron app can obtain the `graphicsCaptureWithoutBorder` restricted capability (uncertain — §7). If it can't be suppressed, surface it as expected behavior to users rather than treating it as a bug (it visually indicates *only that specific window* is being captured, not the whole desktop, which is arguably a feature given the app's own privacy stance).
5. **Do not build on raw PrintWindow**, even with `PW_RENDERFULLCONTENT` — it is undocumented, historically flaky for Chromium specifically, and buys nothing (no border, marginally simpler code) that offsets the reliability risk for the app's core use case.
